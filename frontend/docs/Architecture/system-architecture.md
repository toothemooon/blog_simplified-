# SvelteBlog System Architecture

This document provides a comprehensive overview of the architecture, directory structure, and design patterns used in the SvelteBlog frontend project.

## Technology Overview

SvelteBlog is a modern, lightweight single-page application (SPA) built with:
- **Svelte 4**: The core component framework.
- **Vanilla CSS**: A custom CSS architecture without the use of external CSS frameworks (like Tailwind or Bootstrap).
- **page.js**: A lightweight client-side routing library.
- **Rollup**: The module bundler used for building the application.
- **Vercel**: The deployment platform, specifically configured for SPA routing.

## Architectural Principles & Design Patterns

The project is structured around the following core philosophies:

1. **Feature-based Organization**: Files and components are grouped by their domain or feature (e.g., `blog/`, `projects/`) rather than their technical type (e.g., all views, all controllers).
2. **Component Encapsulation and Separation of Concerns**: Each component handles its own scoped logic and styling. Components are conceptually divided into:
   - **Container Components**: Manage data and state (e.g., `BlogListPage.svelte`).
   - **Presentational Components**: Purely render UI based on provided props (e.g., `ProjectCard.svelte`).
3. **Composition**: Smaller, single-responsibility components are composed to build complex UIs.
4. **Data Centralization**: Core data files are isolated in a dedicated `data/` directory to facilitate easy management and potential future migrations to external APIs or CMS platforms.

## Core Subsystems

### Component Subsystems

Components are strictly categorized to manage complexity:
- **Top-level / Shared Components**: Include `App.svelte` (the main shell), `Header.svelte` (navigation and theme controls), and `AboutPage.svelte`.
- **Blog Components**: Manage the blogging experience. Includes `HomePage.svelte` (recent posts), `BlogListPage.svelte` (all posts with tags sidebar), `BlogPostPage.svelte` (individual article), `TagsPage.svelte` (tag overview), and `TagPage.svelte` (tag filtering).
- **Project Components**: Manage portfolio displays. Includes `ProjectsPage.svelte` (grid layout), `ProjectCard.svelte` (individual previews), and `ProjectDetailPage.svelte` (extended details).

### Styling Architecture

The project employs a hybrid, mobile-first styling strategy:
1. **Global Variables**: `src/global.css` defines root CSS variables for colors, typography, and spacing to maintain consistency.
2. **Component-scoped Styles**: Svelte's built-in style encapsulation ensures component-specific CSS does not leak globally.
3. **Theming System**: Implements a light/dark/system mode toggle relying on scoped CSS variables overrides, class toggling on the `body`/`html`, and local storage to persist user preferences.

### Routing & Application Flow

All routing is managed client-side using `page.js`:
1. **Initialization**: The browser loads `index.html`, which imports `main.js`.
2. **Route Definitions**: `main.js` maps URL paths (including parameterized routes for dynamic posts and projects) to specific components, handling auto-scrolling on navigation.
3. **Rendering**: `App.svelte` dynamically renders the matched component inside the application shell.
4. **SPA Handling**: The sirv development server uses the `--single` flag, and `vercel.json` provides rewrite rules in production to ensure direct URL access serves `index.html` rather than throwing 404 errors.

### Data Management

Blog content uses a modular two-layer approach: post **metadata** (title, date, slug, tags, authors) lives in individual JS files under `src/data/blog/posts/`, while the **body** is a separate Markdown file under `src/data/blog/content/`. Content is loaded on demand via dynamic `import()`. The `blog/index.js` file registers all posts and exposes utility functions (`getPostBySlug`, `getPostContent`). A compatibility shim in `src/utils/blog-utils.js` merges the new system with any legacy data. See [Data Architecture](./data-architecture.md) for full detail.

## Naming Conventions

To maintain consistency across the codebase, the following naming patterns are strictly enforced:
- **Svelte Components**: PascalCase (e.g., `BlogPostPage.svelte`).
- **JavaScript Files**: kebab-case file names, camelCase for internal variables (e.g., `blog-data.js` exporting `blogPosts`).
- **CSS Classes**: kebab-case (e.g., `.post-card`, `.tag-list`).
- **Static Assets (Images)**: kebab-case (e.g., `scenery-avatar.svg`).
